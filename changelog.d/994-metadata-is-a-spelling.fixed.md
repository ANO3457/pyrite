`metadata` is not a field (Andon #994, decision A; ADR-0051 amends ADR-0042 decision 6): `metadata.k`, in a file or a request, is a second spelling of field `k`, one level only, the same as an alias. Every update refusal (a managed field, `type`, `id`, `body` as a key, a link item's shape) is decided on the field a path denotes, whatever its spelling, depth or surface (service, MCP `kb_update`, REST `PATCH`/`PUT`, CLI `--field`/`--append`/`--remove`/`--unset`), and a request path is parsed once at the boundary, so a key such as `status_change_log[0]` or `metadata.id` inside the `metadata` envelope is the field it names. A file that spells a field twice is reported: `index health` gains `double_spellings` (`{kb, id, field, spellings}`, status `warning`) and `qa validate` the rule `field_spelled_twice`; an update of that field is refused until one spelling goes. The model and the index row read such a file the same way (the field's own name first); an undeclared key spelled at the top level and under `metadata:` reads the top-level value. On create, a declared field or an alias sent inside `metadata` lands at its own key. A top-level `aliases:` now resolves a wikilink: the index row carries `aliases` in its `metadata` JSON, so `GET /api/entries/{id}` and `kb_get` return it there for either spelling.
