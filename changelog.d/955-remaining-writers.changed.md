- **Every write of an entry file is operations on its own bytes (#955, B6 P4).** The last four whole-file writers now name what they change and leave the rest as written: `pyrite rename` sets the new `id:` (and stamps `updated_at` where the file carries it) and rewrites `[[old]]` wikilinks only where they are, in a body or a frontmatter value, keeping every comment and a CRLF file's line endings; `pyrite schema migrate` writes exactly what the migration changed (a key added, changed or dropped, and `_schema_version`) instead of re-emitting the entry, and now actually writes a migration's result rather than only stamping the version; `pyrite ids pin` takes the entry's momentary lock around its write, so a pin and an update of one file cannot interleave; software-kb's `migrate-standards` sets the type and unsets `enforced` whatever follows them on the line, keeps the file's line endings, and refuses to overwrite a file already at the new path. The model's own `save` and markdown emitter are gone: a create's text is built onto a skeleton, and a write that changed meanwhile is a `CONFLICT`. A `created_at` or `updated_at` sent back in another spelling of the same instant (a read's `2026-01-15` for a bare date) is the file's value and writes nothing. A rename is refused only for the entry being renamed: a linking file whose frontmatter cannot be patched as values (it does not parse, or holds an anchor) has the wikilinks in its body rewritten and its frontmatter bytes kept, and a file the rename could not touch at all is listed as `files_skipped`, never fatal; a `[[old]]` inside a YAML comment is a comment and is no longer rewritten. `pyrite schema migrate` stamps `_schema_version` only on a result it wrote: a migration that raises is an error in the result and the file keeps its bytes (it is tried again next time), a migration that changes its input in place is written whole, and the command says to run `pyrite index sync` afterwards. A move (rename to a new path, `migrate-standards` into its new folder) publishes the new file and removes the old one as one write under one lock for both paths, removing the old file only while it still holds the bytes read; a source that changed or a target already taken leaves both files as they are. The model's whole-file text reaches no existing entry: `KBRepository.save` writes a new entry only and refuses an existing one (`ENTRY_EXISTS`); an entry is changed through `KBService.apply_operations` alone.
